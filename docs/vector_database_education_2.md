# Chapter 3. 생성형 AI 프로젝트 설계 방법론

## 3.1 생성형 AI 프로젝트 수행 작업 절차

### 1) 왜 별도의 프로젝트 방법론이 필요한가?
생성형 AI 프로젝트는 전통적 IT 구축 프로젝트와 유사한 점도 있지만, 몇 가지 중요한 차이가 있다. 일반적인 정보시스템 구축은 기능 정의, 화면 설계, DB 설계, 개발 및 테스트 중심으로 진행되는 경우가 많다. 반면 생성형 AI 프로젝트는 **문제 정의, 데이터 준비, 모델 선택, 프롬프트 설계, 검색 구조 설계, 품질 평가, 운영 안전장치 설계** 가 성패를 좌우한다.

즉, 생성형 AI 프로젝트는 단순히 모델 API를 연결하는 개발 프로젝트가 아니라, **데이터·모델·업무 프로세스·거버넌스** 를 통합적으로 설계하는 프로젝트라고 볼 수 있다.

### 2) 생성형 AI 프로젝트의 기본 수행 절차
생성형 AI 프로젝트는 크게 **3단계, 7개 세부 절차** 로 수행할 수 있다.

#### 1단계. 비즈니스 목표 이해 및 원천데이터 이해
과제의 목적과 다뤄야 할 데이터를 먼저 명확히 하는 단계다.

##### (1) 비즈니스 목표 이해
가장 먼저 “무엇을 해결할 것인가?”와 “누가, 어떤 업무 흐름에서 사용하는가?”를 명확히 해야 한다.
- 업무 문제는 무엇인가?
- 사용자는 누구이며, 어떤 업무 시나리오에서 사용하는가?
- 결과는 요약, 추천, 분류, 질의응답 중 무엇인가?
- 기대 효과와 성공 기준은 어떻게 측정할 것인가?

예를 들어 “사내 규정 질의응답 챗봇 구축”이라는 과제라면, 단순히 챗봇을 만드는 것이 아니라 **정확한 규정 검색**, **권한 기반 응답**, **최신 문서 반영**, **답변 신뢰성 확보** 가 목표가 될 수 있다.

##### (2) 원천데이터 이해
비즈니스 목표를 달성하기 위해 다뤄야 할 데이터를 파악하는 단계다.
- 어떤 문서/대화/이미지 데이터가 있는가?
- 데이터의 최신성과 정합성은 확보되어 있는가?
- 개인정보 또는 민감정보가 포함되어 있는가?
- 학습용인지, 검색용인지, 평가용인지 구분되는가?

실제 프로젝트에서는 이 단계에서 데이터 품질 문제가 가장 많이 드러난다. 세부 절차는 3.2절과 Chapter 4에서 다룬다.

#### 2단계. 데이터 준비 및 설계, 개발, 평가
목표와 데이터를 바탕으로 실제 시스템을 설계·구현하고 품질을 검증하는 단계다.

##### (3) 데이터 준비 및 설계
원천데이터를 검색·생성에 적합한 형태로 가공하고, 저장 구조를 설계한다.
- 문서 청킹(chunking) 단위 설계
- 메타데이터 항목 설계
- Vector DB의 Collection/스키마 설계

세부 절차는 3.2절 "데이터 분석 준비 및 설계 절차"와 4.2절 "스키마 설계"에서 자세히 다룬다.

##### (4) 개발
설계를 바탕으로 기술 아키텍처를 구축하고 프로토타입을 구현한다.
- 단순 프롬프트 기반인가, RAG 구조가 필요한가?
- 파인튜닝 또는 에이전트형 워크플로우가 필요한가?
- Vector DB, 재정렬기(Reranker), Guardrail 구성
- 프롬프트 초안 작성 및 임베딩/검색 구조 구현

이 단계에서는 기능 요구만 볼 것이 아니라 성능, 비용, 보안, 운영성을 함께 고려해야 하며, PoC의 목적은 “동작 여부 확인”이 아니라 **실제 업무 적용 가능성** 과 **품질 한계** 를 파악하는 데 있다.

##### (5) 평가
생성형 AI는 정답률만으로 품질을 판단하기 어렵다. 다음 요소를 함께 봐야 한다.
- 정확성, 관련성, 환각(hallucination) 여부
- 응답 일관성, 응답 속도, 사용자 만족도

필요하면 프롬프트 개선, 청킹 조정, 임베딩 교체, 검색 파라미터 조정 등을 반복한다. 세부 절차는 4.3절 "검색·응답 품질평가"에서 다룬다.

#### 3단계. 배포, 모니터링 및 개선
검증된 시스템을 실제 서비스로 내보내고, 운영하면서 지속적으로 품질을 관리하는 단계다.

##### (6) 배포
검증이 끝난 시스템을 운영 환경에 반영한다.
- 배포 전 보안·권한 점검
- 트래픽 규모에 맞는 인프라 구성
- 단계적 배포(카나리, 순차 오픈) 여부 결정

##### (7) 모니터링 및 개선
상용화 이후에는 기술 구현보다 운영 체계가 더 중요할 수 있다.
- 로그 수집 및 모니터링
- 사용자 피드백 수집
- 모델 버전 관리, 문서 갱신 주기 관리
- 권한 및 보안 통제, 책임 체계와 검수 프로세스
- 성능/정합성 저하 시 개선 조치 (세부 내용은 4.4절 "성능/정합성 개선" 참고)

### 3) 생성형 AI 프로젝트 절차 예시
다음과 같은 흐름으로 정리할 수 있다.

1. 비즈니스 목표 이해
2. 원천데이터 이해
3. 데이터 준비 및 설계
4. 개발
5. 평가
6. 배포
7. 모니터링 및 개선

### 4) 전통적 AI 프로젝트와의 차이
| 구분 | 전통적 분석/예측 AI | 생성형 AI 프로젝트 |
|---|---|---|
| 핵심 목표 | 예측, 분류, 최적화 | 생성, 요약, 질의응답, 추론 지원 |
| 중요 자산 | 라벨링 데이터, 모델 성능 | 문서/지식 데이터, 프롬프트, 검색 구조 |
| 품질 이슈 | 정확도, 정밀도, 재현율 | 정확성, 환각, 관련성, 응답 일관성 |
| 설계 초점 | 모델 학습과 성능 | 데이터-검색-생성 통합 아키텍처 |
| 운영 포인트 | 재학습 주기 | 문서 갱신, 프롬프트 개선, 안전장치 |

### 5) 교육 포인트 정리
- 생성형 AI 프로젝트는 **비즈니스/데이터 이해 → 준비·개발·평가 → 배포·모니터링** 의 3단계 구조로 이해할 수 있다.
- 모델 선정보다 **문제 정의와 데이터 설계** 가 중요하다.
- PoC는 단순 데모가 아니라 실무 적용 가능성을 검증하는 단계다.
- 상용화 시에는 배포 이후의 모니터링과 개선 체계가 핵심이다.

## 3.2 데이터 분석 준비 및 설계 절차

### 1) 데이터 분석 준비의 중요성
생성형 AI 프로젝트에서 데이터 분석 준비는 단순한 사전 작업이 아니다. 이 단계는 이후의 임베딩 설계, 검색 품질, 응답 정확도, 운영 비용에 직접적인 영향을 준다. 데이터 준비가 부실하면 아무리 우수한 모델과 Vector DB를 사용하더라도 결과 품질이 낮아질 수 있다.

### 2) 데이터 분석 준비 절차

#### (1) 분석 목적 정의
먼저 데이터 분석의 목적을 명확히 해야 한다.
- 어떤 질문에 답하려는가?
- 어떤 사용자 문제를 해결하려는가?
- 어떤 데이터가 필요한가?
- 분석 결과를 어디에 활용할 것인가?

예를 들어 사내 지식검색용 RAG를 설계하는 경우, 목적은 “문서를 요약하는 것”이 아니라 “질문과 관련된 근거 문서를 정확히 찾아 답변을 생성하는 것”일 수 있다.

#### (2) 데이터 소스 식별
분석 대상이 되는 데이터 소스를 목록화한다.
- 정책 문서
- 업무 매뉴얼
- 회의록
- 고객 문의 내역
- FAQ
- 이메일
- 이미지/도면/음성 자료

이때 데이터 소스별 형식, 보유 부서, 접근 권한, 갱신 주기도 함께 확인해야 한다.

#### (3) 데이터 구조 및 품질 점검
데이터를 실제로 확인하면서 다음을 점검한다.
- 파일 형식은 무엇인가?
- 구조화/비정형 중 어느 쪽인가?
- 중복 데이터가 많은가?
- 최신본과 구버전이 혼재되어 있는가?
- 누락, 오기, 깨진 문자, 스캔 품질 문제는 없는가?

#### (4) 활용 단위 설계
생성형 AI에서는 원문 전체를 그대로 넣기보다, 검색 및 처리에 적합한 단위로 분할해야 하는 경우가 많다.
- 문서 단위
- 장/절 단위
- 문단 단위
- 문장 단위
- Q&A 단위

이 과정은 흔히 **청킹(chunking) 설계** 라고 부르며, 검색 품질을 크게 좌우한다.

#### (5) 메타데이터 설계
검색 정확도와 운영 통제를 위해 메타데이터 항목을 설계해야 한다. 이 단계에서는 **어떤 메타데이터가 왜 필요한지(설계 관점)** 를 정의하는 데 초점을 둔다. 실제 필드 타입, 인덱싱 방식 등 구현 세부사항은 4.2절 "스키마 설계"에서 다룬다.
- 문서명
- 부서명
- 작성일/개정일
- 버전 정보
- 카테고리
- 보안 등급
- 작성자/소유자
- 출처 링크

#### (6) 평가 데이터셋 설계
PoC나 운영 단계에서 품질을 측정하려면 평가용 질문-정답 세트가 필요하다.
- 자주 묻는 질문
- 실제 업무 질의 사례
- 정답 문서가 명확한 질문
- 답변 근거를 검증할 수 있는 사례

평가셋이 없으면 시스템이 좋아졌는지 나빠졌는지 객관적으로 판단하기 어렵다.

### 3) 설계 시 고려해야 할 실무 요소

#### (1) 최신성 관리
생성형 AI 시스템은 최신 정보 반영 여부가 중요하다. 따라서 데이터 갱신 주기와 반영 프로세스를 설계해야 한다.

#### (2) 보안과 권한
사내 문서나 고객 데이터는 민감할 수 있으므로, 권한별 검색 통제와 마스킹 정책을 함께 설계해야 한다.

#### (3) 품질 기준 정의
어떤 상태를 “분석 가능한 데이터”로 볼 것인지 기준이 있어야 한다.
- 중복 제거율
- 최신 버전 식별률
- 메타데이터 완성도
- 질문-정답 매핑 가능성

### 4) 교육 포인트 정리
- 데이터 준비는 생성형 AI 품질을 좌우하는 핵심 단계다.
- 소스 식별, 구조 점검, 청킹, 메타데이터, 평가셋 설계가 중요하다.
- 분석 준비 단계에서 최신성, 권한, 품질 기준을 함께 설계해야 한다.
- 메타데이터는 본 절에서 "왜 필요한가"를, 4.2절에서 "어떻게 구현하는가"를 다룬다.

# Chapter 4. 데이터 분석 및 준비

## 4.1 데이터분석
생성형 AI 프로젝트의 데이터 분석은 **범위/유형 분석 → 요건 분석 → 피처 분석 → 데이터셋 확보** 의 순서로 진행한다.

### 1) 데이터 범위/유형 분석

#### (1) 데이터 범위 분석이란?
데이터 범위 분석은 프로젝트에서 다룰 데이터의 **경계(boundary)** 와 **포함 범주(scope)** 를 정의하는 작업이다. 이 과정이 불명확하면 불필요한 데이터까지 포함되어 비용이 늘어나거나, 반대로 중요한 데이터가 누락되어 서비스 품질이 낮아질 수 있다.

#### (2) 데이터 범위 분석의 주요 질문
- 어떤 업무 영역의 데이터를 포함할 것인가?
- 어떤 기간의 데이터를 사용할 것인가?
- 어떤 형식의 데이터를 다룰 것인가?
- 내부 데이터만 사용할 것인가, 외부 공개 데이터도 포함할 것인가?
- 검색 대상과 생성 대상은 동일한가?

#### (3) 데이터 유형 분류
생성형 AI 프로젝트에서는 데이터를 다음과 같이 분류해 볼 수 있다.
- **정형 데이터**: 고객 목록, 상품 정보, 거래 기록, 센서 데이터 등 테이블 형태로 정리된 데이터
- **반정형 데이터**: JSON, XML, 로그 파일, 메타데이터 포함 문서 등 일정한 구조는 있으나 완전한 테이블은 아닌 데이터
- **비정형 데이터**: 보고서, 매뉴얼, 이메일, 회의록, 이미지, 음성 녹취, 동영상 자막 등 생성형 AI에서 가장 많이 다루는 유형

#### (4) 범위 분석의 실무 예시
예를 들어 “사내 인사 규정 챗봇”을 만든다면 다음처럼 범위를 정할 수 있다.
- 포함: 인사 규정, 복무 규정, 휴가 규정, FAQ
- 제외: 급여 원장, 개인별 평가 기록, 외부 홍보자료
- 기간: 최근 3개년 최신 버전 우선
- 형식: PDF, DOCX, 사내 위키 문서

#### (5) 데이터 범위/유형 정리 양식
데이터 범위와 유형은 다음 항목을 열(column)로 구성한 엑셀 형식으로 정리하면 관리와 검토가 용이하다.
- **1레벨 분류**: 데이터가 속한 상위 시스템/서비스 단위 (예: 지식관리시스템, 헬프데스크, AS서비스)
- **2레벨 분류**: 업무영역 기준의 세부 분류 (예: 비즈니스 영역, 개발 영역, Q&A, 게시판, 매뉴얼 등)
- **데이터 유형**: 저장 방식 기준 유형 (예: PPT, RDB Table, HWP 등)
- **데이터 건수**: 관리 대상 데이터량

| 1레벨 분류 | 2레벨 분류 | 데이터 유형 | 데이터 건수 |
|---|---|---|---|
| 지식관리시스템 | 비즈니스 영역 | HWP | 1,200건 |
| 지식관리시스템 | 개발 영역 | PPT | 350건 |
| 헬프데스크 | Q&A | RDB Table | 15,000건 |
| 헬프데스크 | 게시판 | RDB Table | 8,400건 |
| AS서비스 | 매뉴얼 | PPT | 210건 |

이렇게 시스템/업무 영역별로 정리하면 데이터 규모와 형식을 한눈에 파악할 수 있어, 이후 청킹 전략 수립과 4.2절 스키마(Collection) 설계의 기초 자료로 활용할 수 있다.

### 2) 데이터 요건 분석

#### (1) 데이터 요건 분석의 의미
데이터 요건 분석은 프로젝트 목표를 달성하기 위해 데이터가 충족해야 할 조건을 정의하는 작업이다. 단순히 “데이터가 있다/없다”를 확인하는 것이 아니라, **어떤 수준의 품질과 속성** 이 필요한지를 정리하는 과정이다.

도출한 요건은 **요구사항 범주 / 요구사항 정의 / 기타** 형식의 표로 정리하면 실무에서 바로 활용할 수 있다.
- **요구사항 범주**: 데이터 변환, 데이터 서비스, 데이터 보안, 데이터 품질 등
- **요구사항 정의**: 문서의 제목을 기준으로 마크다운 형식 변환, 제목과 본문 사이 한 줄 띄고 변환 등 구체적인 처리 규칙
- **기타**: 해당 요구사항이 적용되는 데이터 형식(텍스트, 표, 이미지 등)을 기록

| 요구사항 범주 | 요구사항 정의 | 기타 |
|---|---|---|
| 데이터 변환 | 문서의 제목을 기준으로 마크다운(Markdown) 형식으로 변환 | 텍스트 |
| 데이터 변환 | 제목과 본문 사이 한 줄을 띄고 변환 | 텍스트 |
| 데이터 서비스 | 검색 결과에 원문 링크와 최신 개정일을 함께 제공 | 텍스트 |
| 데이터 보안 | 보안 등급 3급 이상 문서는 본문 마스킹 처리 후 색인 | 텍스트, 표 |
| 데이터 품질 | 동일 문서의 여러 버전 중 최신본만 색인 대상으로 유지 | 텍스트, 이미지 |

#### (2) 주요 데이터 요건 항목
- **정확성**: 데이터의 내용이 사실과 일치해야 한다. 문서 오류, 중복, 잘못된 버전은 응답 품질을 떨어뜨린다.
- **완전성**: 필요한 정보가 빠짐없이 존재해야 한다. 핵심 문서가 누락되면 검색 결과도 불완전해진다.
- **최신성**: 정책, 가격, 규정처럼 자주 바뀌는 정보는 최신본 유지가 매우 중요하다.
- **일관성**: 동일 개념이 문서마다 다르게 표현되면 검색과 생성 결과에 혼란이 생길 수 있다.
- **접근 가능성**: 데이터가 기술적으로 읽을 수 있는 형식이어야 하며, 시스템이 접근할 수 있어야 한다.
- **보안성**: 민감정보는 적절히 통제되어야 하며, 데이터 처리 범위가 정책에 부합해야 한다.

#### (3) 생성형 AI 관점의 추가 요건
전통적 데이터 요건 외에도 다음 사항이 중요하다.
- 임베딩 가능한 텍스트 품질인가?
- 청킹 시 의미 단위가 유지되는가?
- 메타데이터 필터링이 가능한가?
- 근거 문서 추적이 가능한가?
- 평가 질문과 연결 가능한가?

#### (4) 데이터 요건 명세 예시
| 항목 | 요구 내용 | 점검 예시 |
|---|---|---|
| 정확성 | 최신 승인본만 사용 | 개정 이력 확인 |
| 완전성 | 핵심 정책 문서 100% 확보 | 문서 목록 대조 |
| 최신성 | 월 1회 이상 갱신 반영 | 업데이트 배치 확인 |
| 보안성 | 권한별 접근 통제 적용 | 부서별 접근 정책 확인 |
| 추적성 | 응답 근거 문서 링크 제공 | 메타데이터 설계 확인 |

### 3) 데이터 피처 분석

#### (1) 데이터 피처 분석이란?
데이터 피처(feature) 분석은 데이터가 어떤 속성과 특징을 가지는지 파악하여, 모델 입력과 검색 구조 설계에 활용하는 과정이다. 전통적 머신러닝에서는 피처 엔지니어링이 매우 중요했듯이, 생성형 AI에서도 어떤 정보 단위를 어떻게 표현할지 판단하는 일이 중요하다.

피처 분석의 기본 흐름은 다음과 같다.

```text
[ 원천데이터 ]
      │
      ▼
┌───────────────────────────┐
│ 중요한 특징 선택 (+)        │
│ 불필요한 특징 제거 (-)      │
└───────────────────────────┘
      │
      ▼
   [ 피처 ]
```

즉, 원천데이터에서 검색·생성 품질에 기여하는 특징은 선택해 남기고, 노이즈가 되는 불필요한 특징은 제거하는 과정을 거쳐 실제 활용 가능한 피처가 만들어진다.

#### (2) 생성형 AI에서의 피처 관점
생성형 AI 프로젝트에서 피처는 꼭 숫자 변수만을 의미하지 않는다. 문서 제목, 섹션 구조, 문단 길이, 작성 부서, 작성 시점, 키워드 빈도, 문서 유형, 질의 유형, 사용자 역할 같은 정보도 중요한 피처로 볼 수 있다.

#### (3) 피처 분석의 주요 항목
- **내용 피처**: 문서 본문에 포함된 핵심 개념, 용어, 키워드, 문장 길이, 주제 밀도 등
- **구조 피처**: 제목, 목차, 장/절 구분, 표/리스트 여부 등 문서 구조적 특성. 구조가 잘 보존되면 청킹과 검색 품질이 좋아질 수 있다.
- **메타 피처**: 작성자, 부서, 날짜, 버전, 카테고리 같은 부가 정보. 필터링과 권한 통제에 유용하다.
- **활용 피처**: 어떤 질문에 자주 쓰이는지, 어떤 문서가 많이 참조되는지 같은 사용 로그 기반 특성

#### (4) 피처 분석의 활용 예시
- 문서 길이가 너무 길면 청킹 기준을 더 세밀하게 조정
- 문서 유형별로 다른 프롬프트 전략 적용
- 최신 문서에 높은 우선순위 부여
- 부서별 메타데이터를 활용해 권한 검색 구현
- FAQ형 데이터는 Q&A 단위로 별도 인덱싱

### 4) 데이터셋 확보

#### (1) 데이터셋 확보의 의미
데이터셋 확보는 프로젝트 수행에 필요한 데이터를 수집, 정리, 정제하여 실제 활용 가능한 형태로 준비하는 작업이다. 이 단계는 단순 수집이 아니라 **사용 목적에 맞는 품질의 데이터셋을 구성하는 것** 이 핵심이다.

#### (2) Gold 데이터 수집 절차
Gold 데이터(고품질 기준 데이터)는 다음과 같은 흐름으로 수집한다.

```text
[ 원천데이터 분석 ]
        │
        ▼
┌─────────────────────────────────────┐
│ 중요도를 고려한 데이터 식별            │
│ 벡터 활용 관점에서 중요한 데이터 식별   │
└─────────────────────────────────────┘
        │
        ▼
   [ Gold 데이터 수집 ]
```

- **원천데이터 분석**: 전체 데이터 중 어떤 데이터가 존재하는지 먼저 파악한다.
- **중요도를 고려한 데이터 식별**: 업무 중요도, 조회 빈도, 최신성 등을 기준으로 우선순위가 높은 데이터를 가려낸다.
- **벡터 활용 관점에서 중요한 데이터 식별**: 검색·생성 품질에 실제로 기여할 대표성·커버리지가 높은 데이터를 선별한다.
- 이렇게 선별한 고품질 데이터를 **Gold 데이터** 라 하며, 평가셋과 초기 PoC의 기준 데이터로 활용한다.

#### (3) 데이터셋 확보 절차
- **소스 목록화**: 내부 문서 저장소, 업무 시스템 DB, 협업 도구, 고객센터 기록, 공개 데이터 포털, 외부 계약 문서 등 확보 대상 데이터를 식별
- **수집 및 반입**: 파일 수집, API 연계, DB 추출, 배치 반입, 수동 검수 후 업로드 등 소스별 추출 방법 결정
- **정제 및 표준화**: 파일명 규칙 통일, 문자 인코딩 정리, 중복 제거, 버전 정리, 불필요 페이지 제거, 본문/메타데이터 분리
- **라벨링 또는 평가셋 구축**: 질문-정답, 문서-카테고리, 중요도 태그 등 부여 (생성형 AI 프로젝트에서는 특히 중요)
- **저장 및 관리 체계 확립**: 원본 보존 여부, 전처리본 관리, 버전 관리, 접근 권한, 갱신 이력 관리

#### (4) 내부 데이터와 외부 데이터의 결합
실제 프로젝트에서는 내부 문서만으로 부족한 경우가 있다. 법령/규정 데이터, 공개 통계 데이터, 제품 매뉴얼, 산업 표준 문서, 웹 공개 FAQ 같은 외부 데이터를 함께 활용할 수 있다. 단, 외부 데이터는 저작권, 신뢰성, 최신성, 라이선스 조건을 반드시 검토해야 한다.

#### (5) Q&A 학습 데이터셋 구축 방법
Q&A 형태의 학습·평가 데이터셋은 다음 두 가지 방법을 조합해 구축할 수 있다.
- **전문가 그룹 활용**: 업무 도메인 전문가가 실제 업무에서 자주 발생하는 질문과 정답을 직접 작성한다. 정확도는 높지만 시간과 인력 비용이 크다.
- **LLM 활용**: Gold 데이터를 기반으로 LLM이 질문-정답 쌍 초안을 대량 생성하고, 이를 전문가가 검수·보정한다. 대량 생성이 가능하지만 환각(hallucination)이나 저품질 질문이 섞일 수 있어 검수 프로세스가 필수다.
- 실무에서는 LLM으로 초안을 대량 생성한 뒤 전문가 그룹이 샘플링 검수하는 **하이브리드 방식** 을 많이 사용한다.

LLM 활용 방식은 세부적으로 다음 절차로 진행한다.

```text
[ Gold 데이터셋 ]
        │
        ▼
   프롬프트 작성
        │
        ▼
LLM으로 Question 데이터셋 작성
        │
        ▼
   전문가 수기 검토
        │
        ▼
[ Question 데이터셋 확정 ]
```

- **Gold 데이터셋**: (2)에서 선별한 고품질 데이터를 질문 생성의 입력으로 사용한다.
- **프롬프트 작성**: Gold 데이터로부터 어떤 유형·난이도·형식의 질문을 뽑을지 지시하는 프롬프트를 설계한다.
- **LLM으로 Question 데이터셋 작성**: 설계한 프롬프트로 LLM이 Question 초안을 대량 생성한다.
- **전문가 수기 검토**: 도메인 전문가가 생성된 질문의 타당성, 난이도, 중복 여부를 하나씩 수기로 검토한다.
- **Question 데이터셋 확정**: 검토를 통과한 질문만 최종 데이터셋으로 확정하고, 이후 정답(Answer) 매핑 단계로 이어간다.

#### (6) 평가 데이터셋 구축 절차
평가 데이터셋은 **질문 → Retrieval 데이터 → Response 데이터** 순서로 구성 요소를 채워나가며 만든다.

```text
[ 질문 ]  →  [ Retrieval 데이터 ]  →  [ Response 데이터 ]
```

- **질문(Question)**: 사용자가 실제로 입력할 법한 질의를 정의한다.
- **Retrieval 데이터**: 해당 질문에 대해 Vector DB가 검색한 관련 문서(근거)를 기록한다.
- **Response 데이터**: 검색된 문서를 근거로 생성된 응답을 기록한다.

이 순서로 채워야 이후 4.3절의 Retrieval 검토와 Response 검토를 각각 독립적으로 수행할 수 있다.

평가용 QA 데이터셋 자체는 다음 흐름으로 생성한다.

```text
[ Gold 데이터셋 ]
        │
        ▼
   K개 문장 선별
        │
        ▼
선별 문장 기준 Question 생성
        │
        ▼
  LLM으로 Answer 요청
        │
        ▼
[ QA 평가 데이터셋 생성 ]
```

- **Gold 데이터셋**: (2)에서 확보한 고품질 원천 데이터를 기준으로 삼는다.
- **K개 문장 선별**: Gold 데이터셋에서 대표성 있는 K개 문장(또는 청크)을 선별한다.
- **선별 문장 기준 Question 생성**: 선별된 문장을 근거로, 해당 문장에서만 답할 수 있는 질문을 생성한다.
- **LLM으로 Answer 요청**: 생성된 질문을 LLM에 입력해 정답 초안을 얻는다.
- **QA 평가 데이터셋 생성**: 질문-정답 쌍을 검수해 최종 평가 데이터셋으로 확정한다.

#### (7) 학습/평가 데이터셋 예시
구축한 데이터셋은 다음과 같이 **업무 / Instruction / Input / Output** 형식으로 정리하면 학습·평가에 바로 활용할 수 있다.

| 업무 | Instruction | Input | Output |
|---|---|---|---|
| 사내 규정 질의응답 | 아래 문서를 참고하여 질문에 답하시오. | (문서: 휴가 규정 3조) 질문: 연차는 최대 며칠까지 이월 가능한가요? | 연차는 최대 5일까지 다음 해로 이월할 수 있습니다. |
| 고객 FAQ 요약 | 아래 문의 내용을 한 문장으로 요약하시오. | 고객 문의: 배송이 3일째 지연되고 있는데 환불이 가능한지 문의드립니다. | 배송 지연에 따른 환불 가능 여부 문의 |
| 제품 매뉴얼 검색 | 아래 매뉴얼에서 질문에 해당하는 절차를 안내하시오. | (문서: 제품 매뉴얼 5장) 질문: 초기화는 어떻게 하나요? | 전원 버튼을 10초간 길게 눌러 초기화할 수 있습니다. |

#### (8) 데이터셋 관리 표 예시 (엑셀)
확보한 데이터셋은 다음과 같이 엑셀 표로 관리하면 진행 현황과 품질을 추적하기 쉽다.

| No | 데이터 출처 | 데이터 유형 | 건수 | Gold 여부 | 수집 방법 | 검수 상태 | 비고 |
|---|---|---|---|---|---|---|---|
| 1 | 인사 규정집 | HWP | 120 | Y | 전문가 그룹 | 검수완료 | 최신본 기준 |
| 2 | 고객 FAQ | RDB Table | 3,500 | N | 시스템 추출 | 검수중 | 중복 제거 필요 |
| 3 | Q&A 학습셋 | Text | 800 | Y | LLM 생성 + 전문가 검수 | 검수완료 | 환각 여부 확인 |
| 4 | 제품 매뉴얼 | PPT | 60 | N | 수동 업로드 | 미검수 | 이미지 포함 |

#### (9) 데이터셋 확보 시 주의사항
- 무조건 많은 데이터가 좋은 것은 아니다.
- 중복과 잡음(noise)이 많으면 검색 정확도가 떨어질 수 있다.
- 권한이 없는 데이터 반입은 보안 리스크가 된다.
- 평가 가능한 구조로 정리되지 않으면 품질 개선이 어렵다.

### 5) 교육 포인트 정리
- 데이터 범위는 넓을수록 좋은 것이 아니라, 목적 적합성이 중요하다.
- 데이터 요건은 정확성, 완전성, 최신성, 일관성, 보안성, 추적성까지 포함해야 한다.
- 피처 분석은 청킹, 검색, 프롬프트, 권한 설계에 직접 연결된다.
- 데이터셋 확보는 수집·정제·표준화·관리까지 포함하며, 양보다 목적 적합성과 품질 관리가 중요하다.

## 4.2 스키마 설계
Vector DB에 데이터를 적재하기 전에는 저장 구조인 Collection·Vector·메타데이터·관계(Relationship)를 설계해야 한다. 3.2절에서 정의한 "어떤 메타데이터가 왜 필요한가"를 실제 구현 가능한 스키마로 옮기는 작업이며, 세부 설계 방법은 별도 문서의 **Chapter 5. Vector DataBase Schema 설계** (5.1 Schema 설계, 5.2 Collection Design, 5.3 Vector Design, 5.4 Meta Data Design, 5.5 Relationship Design)에서 자세히 다룬다.

### 1) 스키마 설계에서 결정해야 할 것
- **Collection**: 벡터 데이터를 어떤 단위로 묶을지(업무 도메인, 문서 유형, 보안 등급 등 분리 기준)
- **Vector**: 임베딩 차원, 유사도 계산 방식, ANN 인덱스 종류와 파라미터
- **메타데이터**: 필드 타입, 필터링용 인덱스, 접근 권한(RBAC) 연동 필드
- **관계(Relationship)**: 문서-청크, Collection 간 참조 등 벡터 DB에서 제한적으로 지원되는 관계를 어떻게 표현할지

### 2) 데이터 적재/인덱싱 개요
- 원본 데이터 → 청킹 → 임베딩 → Collection 적재로 이어지는 흐름을 정의한다.
- 인덱스 빌드 시점(즉시 색인 vs 배치 색인)과 증분 데이터 반영 주기를 함께 설계해야 한다.

### 3) 교육 포인트 정리
- 스키마 설계는 Collection, Vector, 메타데이터, 관계까지 함께 고려해야 한다.
- 메타데이터는 "왜 필요한가"(3.2절)와 "어떻게 구현하는가"(Chapter 5)를 구분해서 이해해야 한다.
- 초기 스키마 설계가 부실하면 이후 재설계 비용이 크므로 신중하게 접근해야 한다.

## 4.3 검색·응답 품질평가
스키마 설계와 데이터 적재가 끝나면, 실제 검색(Retrieval)과 생성(Response) 품질을 검증하는 단계로 넘어간다. 세부 평가 지표와 매트릭스, 정확도·환각 중심의 응답 평가 방법은 별도 문서의 **Chapter 6. 데이터 검색/응답 정합성 검증(Retrieval/Response)** 에서 자세히 다룬다.

### 1) Retrieval 검토와 Response 검토
- **Retrieval 검토**: 질의에 대해 관련 문서가 상위에 검색되는지 확인한다. (유사도 임계값, 메타데이터 필터, 청킹 단위 적정성 등을 점검)
- **Response 검토**: 검색된 문서를 근거로 생성된 응답의 품질을 확인한다. (정확성, 관련성, 환각 여부, 근거 문서 인용 여부 등을 점검)

### 2) 검색/응답 평가 개요
- 3.2절에서 설계한 평가 데이터셋(질문-정답 세트)을 활용해 반복 측정한다.
- 정량 평가(지표 기반)와 정성 평가(전문가·사용자 검수)를 함께 활용해야 신뢰도 높은 평가가 가능하다.
- 평가 결과는 4.4절 "성능/정합성 개선"의 입력으로 활용된다.

### 3) 교육 포인트 정리
- 품질평가는 Retrieval과 Response를 분리해서 검토해야 원인 파악이 쉽다.
- 정량 지표와 정성 검수를 함께 활용해야 신뢰도 높은 평가가 가능하다.
- 평가셋 없이는 개선 효과를 객관적으로 판단하기 어렵다.
- 구체적인 평가 매트릭스와 사례는 Chapter 6을 참고한다.

## 4.4 성능/정합성 개선
품질평가에서 드러난 문제를 바탕으로 시스템 성능과 데이터 정합성을 개선하는 단계다.

### 1) Collection 분산
- 데이터량 증가에 따라 Collection을 샤딩하거나 복제(replica)를 구성해 처리량과 가용성을 높인다.
- 특정 Collection에 트래픽이 몰릴 경우 별도 노드로 분리 배치하는 것을 검토한다.

### 2) Vector 조정
- 벡터 차원 축소(PQ 등)로 저장 공간과 검색 속도를 개선하거나, ANN 인덱스 파라미터(M, ef, nlist 등)를 재조정한다.
- 유사도 계산 방식 변경이 검색 품질에 미치는 영향을 재검증한다.

### 3) 검색전략 조정
- 벡터 검색과 키워드 검색(BM25)을 결합한 하이브리드 검색을 적용한다.
- 재정렬(Reranking) 모델을 도입해 상위 검색 결과 품질을 개선한다.
- 메타데이터 필터 조건을 재설계해 검색 범위를 최적화한다.

### 4) 모델 변경
- 임베딩 모델을 교체해 의미 표현력을 개선한다(단, 기존 벡터의 재임베딩이 필요할 수 있다).
- 생성 모델(LLM)을 교체하거나 프롬프트 전략을 변경해 응답 품질을 개선한다.

### 5) DB로직 개선
- 인덱싱 알고리즘 변경 또는 파라미터 튜닝을 수행한다.
- 쿼리 실행 계획을 최적화하고 캐싱 전략을 도입한다.
- 중복 제거, 최신본 우선순위 처리 같은 데이터 정합성 점검 로직을 개선한다.

### 6) 교육 포인트 정리
- 성능/정합성 개선은 Collection, Vector, 검색전략, 모델, DB로직 등 다양한 층위에서 접근할 수 있다.
- 개선은 4.3절의 평가 결과를 근거로 우선순위를 정해 진행해야 한다.
- 하나의 개선이 다른 요소에 영향을 줄 수 있으므로, 개선 후에는 반드시 재평가를 수행해야 한다.

# 결론
생성형 AI 프로젝트는 모델을 선택하고 연결하는 것만으로 완성되지 않는다. 비즈니스 목표와 원천데이터를 이해하고, 데이터를 준비·설계하며, 개발과 평가를 거쳐 배포 이후에도 지속적으로 모니터링하고 개선하는 체계적인 절차가 뒷받침되어야 실제 업무에 적용 가능한 서비스가 만들어진다. 특히 데이터 분석 및 준비 단계는 **데이터분석 → 스키마 설계 → 검색·응답 품질평가 → 성능/정합성 개선** 의 흐름으로 이어지며, 이후 임베딩, 검색, 생성 품질에 직접적인 영향을 미친다.

교육 현장에서는 다음 세 가지 관점을 함께 강조하는 것이 중요하다.

- **방법론 관점**: 비즈니스/데이터 이해 → 준비·개발·평가 → 배포·모니터링으로 이어지는 절차적 접근
- **데이터 관점**: 범위·요건·피처 분석과 스키마 설계를 통한 체계적 데이터 준비
- **품질 관점**: 검색·응답 품질평가와 성능/정합성 개선을 통한 지속적 품질 관리

즉, 생성형 AI 프로젝트는 기술 도입 프로젝트가 아니라 **데이터와 프로세스를 함께 설계하는 통합 프로젝트** 로 이해할 필요가 있다.
