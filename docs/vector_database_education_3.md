# Chapter 5. Vector DataBase Schema 설계

## 5.1 Vector DB Schema 설계

### 1) Schema 설계란 무엇인가?
Vector DB Schema 설계는 벡터와 메타데이터를 어떤 구조로 저장하고, 어떻게 검색·필터링·관계 처리를 할 것인지 미리 정의하는 작업이다. 전통적 RDB의 테이블/컬럼 설계와 유사한 개념이지만, Vector DB는 유사도 검색을 중심으로 설계되므로 고려해야 할 요소가 다르다.

### 2) 왜 Schema 설계가 중요한가?
- 스키마를 잘못 설계하면 이후 대규모 재적재(re-indexing)와 재임베딩이 필요할 수 있다.
- 검색 정확도, 응답 속도, 운영 비용이 스키마 구조에 크게 좌우된다.
- 여러 서비스가 하나의 Vector DB를 공유하는 경우, 스키마 설계가 곧 서비스 간 격리와 확장성의 기준이 된다.

### 3) Schema 설계의 4대 구성 요소
Vector DB Schema는 크게 다음 네 가지 설계 영역으로 구성된다.

| 설계 영역 | 핵심 질문 | 관련 절 |
|---|---|---|
| Collection Design | 데이터를 어떤 단위로 묶을 것인가? | 5.2 |
| Vector Design | 벡터를 어떤 차원·인덱스로 저장할 것인가? | 5.3 |
| Meta Data Design | 어떤 부가 정보를 어떤 형태로 저장할 것인가? | 5.4 |
| Relationship Design | 데이터 간 관계를 어떻게 표현할 것인가? | 5.5 |

### 4) Schema 설계 절차 개관
```text
[ 요구사항/데이터 분석 결과 ]  (Chapter 4)
            │
            ▼
   Collection Design (5.2)
            │
            ▼
     Vector Design (5.3)
            │
            ▼
   Meta Data Design (5.4)
            │
            ▼
 Relationship Design (5.5)
            │
            ▼
  [ Schema 확정 → 적재/인덱싱 ]
```

Schema 설계는 Chapter 4에서 수행한 데이터 범위/요건/피처 분석 결과를 입력으로 삼아 진행하며, 네 영역을 순서대로 설계하되 실제로는 반복적으로 검토·조정하는 경우가 많다.

### 5) 교육 포인트 정리
- Schema 설계는 검색 품질과 운영 비용을 동시에 좌우하는 핵심 작업이다.
- Collection, Vector, Meta Data, Relationship 네 영역을 함께 고려해야 한다.
- Schema는 한 번 정해지면 변경 비용이 크므로, 데이터 분석 결과를 충분히 반영해 설계해야 한다.

## 5.2 Collection Design

### 1) Collection이란?
Collection은 RDB의 테이블과 유사한 개념으로, 동일한 스키마(벡터 차원, 메타데이터 필드 구조)를 공유하는 데이터의 논리적 묶음이다. Milvus·Qdrant는 Collection, Pinecone은 Index, Weaviate는 Class라는 이름을 쓰지만 개념은 동일하다.

일반적인 Collection의 스키마는 **원천문장(Source Text), 벡터(Vector), 메타(Meta)** 세 구조로 이루어진다.
- **원천문장**: 임베딩의 근거가 되는 원본 텍스트(청크)
- **벡터**: 원천문장을 임베딩 모델로 변환한 고차원 수치 표현
- **메타**: 원천문장·벡터에 부가되는 속성 정보(문서명, 부서, 작성일 등)

Collection 기반 검색은 키워드의 정확한 일치가 아니라, **데이터가 가진 의미 간 상관관계** 를 기반으로 한 검색이다. 즉 원천문장을 벡터로 표현해 서로 다른 문장이라도 의미적으로 가까우면 유사한 결과로 검색되며, 메타 구조는 이 의미 기반 검색 결과를 조건에 맞게 좁히는 역할을 한다.

### 2) Collection 분리 기준
- **업무 도메인 기준**: 인사, 영업, 고객지원 등 도메인별로 분리
- **문서 유형 기준**: 정책 문서, FAQ, 매뉴얼 등 성격이 다른 데이터를 분리
- **보안 등급 기준**: 접근 권한 수준이 다른 데이터를 분리해 권한 관리를 단순화
- **임베딩 모델 기준**: 차원이 다른 임베딩 모델을 사용하는 데이터는 반드시 Collection을 분리해야 한다.
- **갱신 주기 기준**: 실시간 갱신이 필요한 데이터와 정적 데이터를 분리하면 운영이 단순해진다.

### 3) Collection 설계 단위 기준
업무 도메인 같은 상위 기준을 정했다면, 실제 Collection의 크기와 개수는 다음 세 가지 운영 관점의 기준으로 결정한다.

- **데이터 크기·스케일링**: 데이터량이 하나의 Collection에 집중되면 검색 지연이 증가하므로, 향후 증가량을 감안해 분산·샤딩이 용이한 단위로 나눈다.
- **데이터 접근 패턴**: 자주 함께 조회되는 데이터는 같은 Collection에, 조회 목적·빈도가 다른 데이터는 별도 Collection으로 분리해 캐싱·인덱스 전략을 다르게 적용할 수 있다.
- **데이터 생명주기**: 보관 기간, 삭제·아카이빙 주기가 다른 데이터를 같은 Collection에 두면 일괄 삭제나 TTL(Time-To-Live) 관리가 어려워지므로, 생명주기가 유사한 데이터끼리 묶는 것이 좋다.- **데이터 속성** : 비슷한 속성의 데이터끼리 묶어서 관리하면 검색과 인덱싱이 효과적이다.
- **운영 및 관리의 용이성** : 적절한 단위로 분할한다.

**예시: 뉴스 기사 데이터의 Collection 설계**

| 설계 기준 | 방식 | 장점 | 단점 |
|---|---|---|---|
| 날짜 기준 | 월별·분기별로 Collection 분리 (예: `news_2026_01`, `news_2026_02`) | 오래된 데이터의 아카이빙·삭제가 쉬움, 신규 데이터 적재 성능 유지 | 기간을 넘나드는 검색 시 여러 Collection을 함께 조회해야 함 |
| 주제/카테고리 기준 | 정치, 경제, IT, 스포츠 등 주제별로 Collection 분리 (예: `news_it`, `news_economy`) | 특정 주제 내 검색 정확도 향상, 주제별 접근 권한 관리 용이 | 최신순 조회처럼 날짜 기반 질의에는 비효율적 |
| 혼합 기준 | 주제로 1차 분리 후 각 주제 내에서 다시 연도로 세분화 (예: `news_it_2026`) | 주제 검색과 최신성 관리를 동시에 확보 | Collection 수가 늘어나 운영 복잡도 증가 |

뉴스 기사처럼 데이터가 지속적으로 대량 발생하는 경우, 초기에는 단순한 기준(예: 주제별)으로 시작하고 데이터량이 늘어나면 날짜 기준을 추가하는 **점진적 확장 방식** 을 많이 사용한다.

### 4) Collection 통합 vs 분리 트레이드오프
| 구분 | 통합(단일 Collection) | 분리(다중 Collection) |
|---|---|---|
| 검색 범위 | 넓음(정확도 저하 가능) | 좁음(정확도 향상) |
| 권한 관리 | 메타데이터 필터로 처리 필요 | Collection 단위로 명확히 분리 |
| 운영 복잡도 | 낮음 | Collection 수만큼 증가 |
| 확장성 | 단일 인덱스 크기 증가 | Collection별 독립 확장 가능 |

### 5) Collection 설계 시 정의할 항목
- Collection 이름 규칙(네이밍 컨벤션)
- 벡터 차원 및 인덱스 타입(5.3절과 연계)
- 메타데이터 필드 목록(5.4절과 연계)
- 샤드(shard) 수, 복제(replica) 수
- 생성/삭제/버전 관리 정책

### 6) 실무 예시
사내 지식검색 챗봇을 구축한다면 다음처럼 Collection을 설계할 수 있다.
- `hr_policy_collection`: 인사 정책 문서 (보안 등급 높음)
- `customer_faq_collection`: 고객 FAQ (실시간 갱신 빈번)
- `product_manual_collection`: 제품 매뉴얼 (정적 데이터, 이미지 포함)

### 7) 자주 묻는 질문 (FAQ)

**Q1. 유사한 유형의 데이터라도 업무·쓰임새가 다르면 단일 Collection과 멀티 Collection 중 무엇을 선택해야 하는가?**
데이터 형식(예: 모두 텍스트 문서)이 같더라도 업무 목적과 쓰임새가 다르면 원칙적으로 **멀티 Collection** 을 권장한다. 예를 들어 "인사 규정"과 "고객 FAQ"는 둘 다 텍스트 문서이지만 조회 주체·보안 등급·갱신 주기가 다르므로, 하나로 묶으면 검색 정확도(관련 없는 도메인의 문서가 함께 검색됨)와 권한 관리가 모두 어려워진다. 다만 데이터량이 매우 적고 조회 패턴이 단순한 초기 PoC 단계에서는 운영 부담을 줄이기 위해 단일 Collection과 메타데이터 필터로 시작한 뒤, 서비스가 커지면 분리하는 방식도 가능하다.

**Q2. 텍스트, 이미지 등 서로 다른 유형의 데이터를 하나의 Collection에서 관리할 수 있는가?**
기술적으로는 벡터 차원과 유사도 계산 방식만 동일하면 하나의 Collection에 저장할 수 있지만, 일반적으로는 **권장되지 않는다.** 텍스트와 이미지는 대부분 서로 다른 임베딩 모델(차원, 임베딩 공간)을 사용하므로, 벡터 공간이 다른 데이터를 같은 Collection에서 유사도 비교하면 의미 없는 결과가 나온다. 멀티모달 임베딩 모델(텍스트·이미지를 동일 벡터 공간에 매핑)을 사용하는 경우에 한해 하나의 Collection에서 관리할 수 있으며, 이때도 데이터 유형을 구분하는 메타데이터 필드(`data_type: text/image`)를 함께 설계하는 것이 일반적이다.

**Q3. 하나의 Collection이 다른 Collection의 데이터를 사용해 유사도 검색을 할 수 있는가?**
대부분의 Vector DB는 **Collection 간 직접적인 유사도 검색(cross-collection search)을 기본 기능으로 지원하지 않는다.** 유사도 검색은 원칙적으로 하나의 Collection 내부에서만 수행된다. 여러 Collection에 걸친 검색이 필요하다면 다음과 같은 방법을 사용한다.
- 애플리케이션 레벨에서 각 Collection에 개별적으로 질의한 뒤 결과를 병합·재정렬(rerank)하는 방식
- 검색 대상 데이터를 처음부터 하나의 Collection으로 설계하고, 메타데이터 필드(`source_collection` 등)로 구분해 필터링하는 방식
- 관계 연결이 필요한 경우 5.5절 "Relationship Design"에서 다룬 메타데이터 참조(`ref_collection`, `ref_id`)로 결과를 이어붙이는 방식

즉 "다른 Collection의 데이터를 함께 활용한 검색"은 가능하지만, 이는 Vector DB 자체의 기능이 아니라 **애플리케이션 설계로 구현하는 영역** 이라는 점을 이해해야 한다.

### 8) 교육 포인트 정리
- Collection은 검색 범위와 권한 관리의 기본 단위다.
- 분리 기준은 업무 도메인, 문서 유형, 보안 등급, 임베딩 모델, 갱신 주기 등이 있고, 실제 단위는 데이터 크기·접근 패턴·생명주기를 함께 고려해 정한다.
- 지나친 세분화는 운영 복잡도를 높이므로 통합·분리의 트레이드오프를 함께 검토해야 한다.
- 서로 다른 임베딩 공간을 갖는 데이터(예: 텍스트-이미지)는 원칙적으로 Collection을 분리하고, Collection 간 검색은 Vector DB 기능이 아닌 애플리케이션 설계로 구현해야 한다.

## 5.3 Vector Design

### 1) Vector Design이란?
Vector Design은 임베딩 벡터를 어떤 차원과 인덱스 구조로 저장하고, 어떤 방식으로 유사도를 계산할지 정의하는 작업이다. 검색 속도, 정확도(recall), 저장 비용이 이 설계에 직접적으로 영향을 받는다.

### 2) 문서에서 벡터까지의 흐름 (청킹 개요)
문서는 통째로 임베딩하지 않고, **청킹(Chunking)** 을 거쳐 여러 개의 청크로 분할한 뒤 각 청크를 벡터로 변환한다.

```text
[ 문서 ]
   │
   ▼
 청킹(Chunking)
   │
   ▼
[ 청크1 ]  [ 청크2 ]  [ 청크3 ]  ...
```

### 3) 벡터의 유형: Sparse vs Dense
Vector Design에서는 벡터를 크게 Sparse 벡터와 Dense 벡터 두 가지로 나눠볼 수 있다.

| 구분 | 설명 | 예시 |
|---|---|---|
| Sparse 벡터 | 대부분의 값이 0이고 차원이 큰 벡터. 사람의 언어적 표현을 특정 위치에 값을 채우는 방식으로 매핑한다. | 사람의 언어 "파란색" → 컴퓨터 언어 `[0, 0, 255]`처럼 특정 위치에만 값이 채워짐 |
| Dense 벡터 | 대부분의 값이 0이 아니고 차원은 작지만 의미를 압축적으로 담은 벡터. 임베딩 모델이 학습한 의미 공간의 좌표에 가깝다. | "파란색" → `[2, 255]`처럼 소수의 차원에 의미가 압축되어 표현됨 |

- Sparse 벡터는 키워드 검색(BM25 등)과 유사하게 정확한 용어 일치에 강하다.
- Dense 벡터는 의미 기반 유사도 검색에 강하며, 표현은 다르지만 의미가 같은 문장도 찾아낼 수 있다.

### 4) 벡터 구조 설계
Collection에 저장할 벡터 레코드는 다음 두 가지 구조 중 하나로 설계할 수 있다.
1. **단일 벡터 구조**: 벡터ID, 문장 내용, 벡터
2. **하이브리드 벡터 구조**: 벡터ID, 문장 내용, Sparse 벡터, Dense 벡터

### 5) Sparse·Dense 벡터를 함께 관리하는 이유
두 가지 벡터를 함께 관리하면 더 유연한 검색과 분석 기능을 확보할 수 있다.
1. **다양한 인덱싱 전략**: Sparse용 인덱스와 Dense용 ANN 인덱스를 각각 최적화해 적용할 수 있다.
2. **복합 검색 기능**: 키워드 기반 검색(Sparse)과 의미 기반 검색(Dense)을 결합한 하이브리드 검색이 가능하다.
3. **확장성**: 새로운 임베딩 모델이나 검색 알고리즘을 도입할 때 기존 구조를 유지하면서 확장할 수 있다.

### 6) 청킹 방법
문서를 청크로 나누는 방법은 크게 두 가지로 구분한다.
- **휴리스틱(Heuristic) 방법**: 문자 수, 문단, 구두점처럼 규칙 기반으로 청크 경계를 정하는 방법. 구현이 간단하고 처리 속도가 빠르다.
- **의미 기반(Semantic) 방법**: 문장·문단 간 의미적 유사도를 계산해 의미가 이어지는 부분까지 하나의 청크로 묶는 방법. 정확도는 높지만 계산 비용이 크다.

### 7) 적절한 청크 크기 찾기: 문서 파편화 전략
- **고정 크기 청크(Fixed Size)**: 모든 청크를 동일한 길이(토큰 수 등)로 분할한다. 구현이 단순하지만 문맥이 중간에 끊길 수 있다.
- **콘텐츠 크기에 따른 가변 크기 청크(Dynamic Size)**: 콘텐츠의 구조(문단, 섹션 등)에 따라 청크 길이를 다르게 설정한다. 문맥 보존에는 유리하지만 설계·구현이 더 복잡하다.

### 8) 청크 크기와 응답시간의 상관관계
- **데이터 응답 생성시간 관점**: 청크가 클수록 검색된 컨텍스트 양이 늘어나 LLM 입력 토큰이 많아지고, 응답 생성 시간이 길어질 수 있다.
- **데이터 정확성 관점**: 청크가 너무 작으면 문맥이 부족해 답변 근거가 불충분해지고, 너무 크면 불필요한 정보가 섞여 정확도가 떨어질 수 있다. 적정 청크 크기는 결국 응답 속도와 정확성 사이의 균형점을 찾는 문제다.

### 9) 청킹 전략 수립 시 고려사항
- 색인이 생성되는 콘텐츠의 성격(정형/비정형, 문서 구조 유무)
- 어떤 임베딩 모델을 사용하며, 그 모델에 어떤 청크 크기가 최적인가
- 검색 결과가 어떤 애플리케이션(챗봇, 요약, 추천 등)에서 활용되는가

### 10) 청킹 전략 비교
| 전략 | 설명 | 장점 | 단점 |
|---|---|---|---|
| Fixed Size Chunking | 고정된 토큰·문자 수로 문서를 분할 | 구현이 단순하고 처리 속도가 빠름 | 문맥이 중간에 끊길 수 있음 |
| Content Aware | 문단, 헤더 등 문서의 구조적 요소를 기준으로 분할 | 문서 구조를 보존해 문맥 유지에 유리 | 구조가 불명확한 문서에는 적용이 어려움 |
| Overlapping | 인접 청크 간 일부 구간을 중복시켜 분할 | 청크 경계에서 문맥 단절을 완화 | 저장 공간과 인덱싱 비용 증가 |
| Recursive | 큰 단위(문서)부터 점점 작은 단위(문단→문장)로 재귀적으로 분할 | 다양한 문서 길이에 유연하게 대응 | 재귀 깊이·규칙 설계가 복잡함 |
| Dynamic Size Chunking | 콘텐츠 길이·구조에 따라 청크 크기를 가변적으로 조정 | 문맥 보존과 크기 효율의 균형 확보 | 규칙·임계값 설정에 튜닝이 필요 |
| Semantic | 문장 임베딩 유사도를 기준으로 의미 단위로 분할 | 의미적으로 응집된 청크 생성 가능 | 임베딩 계산 비용이 크고 속도가 느림 |
| Hierarchical | 문서를 장/절/문단 등 계층 구조로 분할·저장 | 상위-하위 문맥을 함께 활용 가능 | 구조 설계·관리가 복잡함(5.5절 관계 설계 연계) |
| Domain specific | 법률 조항, 계약서 조 항목 등 도메인 규칙에 맞춰 분할 | 도메인 특화 정확도가 높음 | 도메인마다 별도 규칙 개발이 필요 |
| Summarization | 청크 대신 문서를 요약한 내용을 색인 | 검색 대상 데이터 크기를 줄일 수 있음 | 요약 과정에서 세부 정보 손실 가능 |
| Extract Candidate | 문서에서 핵심 후보 문장·구절만 추출해 색인 | 노이즈를 줄이고 핵심 정보 위주로 검색 가능 | 추출 기준에 따라 중요한 정보가 누락될 위험 |
| Parent Child | 작은 청크(Child)로 검색하고 상위 문맥(Parent)을 함께 반환 | 검색 정확도와 문맥 제공을 동시에 확보 | 부모-자식 관계 관리(5.5절)가 추가로 필요 |

### 11) 벡터 차원(Dimension) 결정
- 사용할 임베딩 모델의 출력 차원을 그대로 따르는 것이 기본이다(예: 384, 768, 1536차원).
- 차원이 클수록 표현력은 높아지지만 저장 공간과 연산량이 증가한다.
- 하나의 Collection에는 동일한 차원의 벡터만 저장할 수 있으므로, 임베딩 모델 교체 시 재임베딩이 필요하다.

### 12) 유사도 계산 방식 선택
| 방식 | 특징 | 적합한 경우 |
|---|---|---|
| Cosine Similarity | 벡터의 방향(각도) 기준 | 텍스트 임베딩 검색 전반 |
| Euclidean Distance | 벡터 간 직선 거리 기준 | 이미지 등 크기 차이가 의미 있는 경우 |
| Dot Product | 내적 값 기준, 벡터 크기까지 반영 | 추천 시스템, 정규화된 임베딩 |

### 13) ANN 인덱스 설계
- **HNSW**: 그래프 기반 인덱스로 검색 속도와 정확도의 균형이 좋음. `M`(연결 수), `efConstruction`(구축 시 탐색 폭), `ef`(검색 시 탐색 폭) 파라미터로 성능을 조정한다.
- **IVF**: 벡터 공간을 클러스터로 나눠 탐색 범위를 좁히는 방식. `nlist`(클러스터 수), `nprobe`(탐색할 클러스터 수)로 조정한다.
- **PQ(Product Quantization)**: 벡터를 압축해 저장 공간과 연산량을 줄이는 방식. 정확도와 압축률의 트레이드오프가 있다.
- 실무에서는 HNSW+PQ, IVF+PQ처럼 인덱스를 조합해 사용하는 경우가 많다.

### 14) 재임베딩(Re-embedding) 전략
- 임베딩 모델을 교체하거나 업그레이드할 경우, 기존 벡터 전체를 재생성해야 한다.
- 대규모 데이터의 경우 재임베딩 비용이 크므로, 신규 Collection에 우선 적재한 뒤 점진적으로 전환하는 **블루/그린 방식** 을 고려할 수 있다.

### 15) 교육 포인트 정리
- 문서는 청킹을 거쳐 여러 청크로 분할된 뒤 벡터로 변환된다.
- Sparse 벡터와 Dense 벡터를 함께 관리하면 다양한 인덱싱 전략, 복합 검색, 확장성 측면에서 유리하다.
- 청킹 방법은 휴리스틱과 의미 기반으로 나뉘며, 청크 크기는 고정/가변 전략 중 선택할 수 있다.
- 청크 크기는 응답 생성시간과 정확성 사이의 트레이드오프를 고려해 정해야 한다.
- Vector Design은 차원, 유사도 계산 방식, ANN 인덱스를 함께 결정하는 작업이다.
- 인덱스 파라미터는 속도와 정확도 사이의 트레이드오프를 조정하는 수단이다.
- 임베딩 모델 교체는 재임베딩 비용을 수반하므로 신중히 결정해야 한다.

## 5.4 Meta Data Design

### 1) Meta Data Design이란?
메타데이터 설계는 벡터와 함께 저장할 부가 정보(필드)의 구조를 정의하는 작업이다. 3.2절에서 정의한 "어떤 메타데이터가 왜 필요한가"를 실제 필드 타입과 인덱스로 구현하는 단계다.

### 2) 메타데이터 필드 설계 항목
- 필드명과 데이터 타입(문자열, 숫자, 날짜, boolean, enum 등)
- 필수/선택 여부
- 필터링 대상 여부(검색 시 조건절로 사용할지)
- 다중값 허용 여부(예: 태그처럼 여러 값을 가질 수 있는 필드)

### 3) 필터링 성능을 위한 인덱스 설계
- 자주 필터링에 사용되는 필드(예: 부서, 카테고리, 작성일)는 별도의 스칼라 인덱스(secondary index)를 구성해 필터링 성능을 높인다.
- 필터 조건이 많아질수록 벡터 검색과 필터링을 함께 최적화하는 하이브리드 쿼리 성능을 검토해야 한다.

### 4) 보안·권한 연동 필드 설계
- 보안 등급, 부서, 소유자 같은 필드는 역할기반 접근제어(RBAC)와 연동해 설계한다.
- 검색 시 사용자 권한에 따라 메타데이터 필터가 자동으로 추가되도록 설계하면 별도 애플리케이션 로직 없이도 접근 통제가 가능하다.

### 5) 스키마 변경(Schema Evolution) 대응
- 서비스 운영 중 메타데이터 필드가 추가·변경될 수 있으므로, 스키마 변경에 유연한 구조(예: 동적 필드 지원 여부)를 사전에 확인해야 한다.
- 필드 변경 시 기존 데이터에 대한 마이그레이션 계획을 함께 수립해야 한다.

### 6) 메타데이터 필드 설계 예시
| 필드명 | 타입 | 필터링 | 설명 |
|---|---|---|---|
| doc_title | string | Y | 문서 제목 |
| department | string | Y | 작성 부서 |
| created_at | date | Y | 작성일 |
| security_level | enum | Y | 보안 등급(1~5) |
| tags | array(string) | N | 검색 편의를 위한 태그 |

### 7) 교육 포인트 정리
- 메타데이터 설계는 필드 타입, 필터링 인덱스, 보안 연동을 함께 고려해야 한다.
- 자주 필터링되는 필드는 인덱스를 구성해 하이브리드 쿼리 성능을 확보해야 한다.
- 운영 중 스키마 변경 가능성을 고려해 유연한 구조로 설계하는 것이 바람직하다.

## 5.5 Relationship Design

### 1) Vector DB에서 관계(Relationship) 설계가 필요한 이유
전통적 RDB는 외래키(Foreign Key)와 조인(Join)으로 테이블 간 관계를 표현하지만, 대부분의 Vector DB는 조인을 지원하지 않거나 제한적으로만 지원한다. 따라서 문서-청크, 상위-하위 문서, Collection 간 참조 같은 관계를 메타데이터와 애플리케이션 로직을 조합해 표현해야 한다.

### 2) 대표적인 관계 유형
- **문서-청크(Document-Chunk) 관계**: 하나의 원본 문서가 여러 개의 청크(벡터)로 분할되는 1:N 관계
- **상위-하위 문서 관계**: 장/절/조항처럼 계층 구조를 가지는 문서의 부모-자식 관계
- **Collection 간 참조 관계**: 서로 다른 Collection에 저장된 데이터 간의 연관관계(예: FAQ 답변이 정책 문서를 참조)
- **버전 관계**: 동일 문서의 여러 개정판 간의 관계(최신본 우선순위 포함)

### 3) 관계 표현 방법
- **메타데이터를 통한 참조**: 청크 메타데이터에 `parent_doc_id`, `chunk_index` 같은 필드를 두어 상위 문서와의 관계를 표현한다.
- **계층 정보 인코딩**: `section_path`(예: "3장 > 2절 > 1항")처럼 계층 경로를 메타데이터에 저장해 상위-하위 관계를 표현한다.
- **애플리케이션 레벨 조인**: 검색 결과로 얻은 청크의 `parent_doc_id`를 이용해 별도로 원본 문서나 관련 메타데이터를 조회(RDB 또는 다른 Collection에서)하는 방식이다.
- **그래프 DB 병행 사용**: 관계가 복잡한 경우(다대다 관계, 지식 그래프) Vector DB와 별도로 그래프 DB를 함께 사용하는 하이브리드 아키텍처를 고려할 수 있다.

### 4) 관계 설계 시 고려사항
- 관계가 복잡할수록 애플리케이션 레벨에서 처리해야 할 로직이 늘어나므로, 꼭 필요한 관계만 스키마에 반영한다.
- 상위 문서 정보가 자주 필요하다면, 검색 성능을 위해 일부 상위 문서 정보(제목, 카테고리 등)를 청크 메타데이터에 **중복 저장(비정규화)** 하는 것이 유리할 수 있다.
- 관계 필드는 필터링·조인 빈도를 고려해 인덱스 여부를 결정한다(5.4절 참고).

### 5) 관계 설계 예시
| 관계 유형 | 표현 방법 | 예시 필드 |
|---|---|---|
| 문서-청크 | 메타데이터 참조 | `parent_doc_id`, `chunk_index` |
| 상위-하위 문서 | 계층 경로 인코딩 | `section_path` |
| Collection 간 참조 | 애플리케이션 레벨 조인 | `ref_collection`, `ref_id` |
| 버전 | 메타데이터 + 최신본 플래그 | `doc_version`, `is_latest` |

### 6) 교육 포인트 정리
- Vector DB는 RDB와 달리 조인을 지원하지 않으므로, 관계는 메타데이터와 애플리케이션 로직으로 설계해야 한다.
- 문서-청크, 계층, Collection 간 참조, 버전 관계가 대표적인 유형이다.
- 검색 성능이 중요한 필드는 비정규화(중복 저장)를, 관계가 복잡한 경우 그래프 DB 병행을 고려할 수 있다.

# 결론
Vector Database Schema 설계는 Collection, Vector, Meta Data, Relationship 네 영역을 유기적으로 고려해야 하는 작업이다. Collection은 검색 범위와 권한 관리의 단위를, Vector 설계는 검색 속도와 정확도를, Meta Data 설계는 필터링과 보안 통제를, Relationship 설계는 조인을 지원하지 않는 Vector DB의 한계를 보완하는 역할을 한다.

교육 현장에서는 다음 관점을 함께 강조하는 것이 중요하다.

- **구조 관점**: Collection 분리 기준과 통합·분리의 트레이드오프
- **성능 관점**: 벡터 차원, 유사도 계산, ANN 인덱스 파라미터 튜닝
- **운영 관점**: 메타데이터 기반 필터링·보안 통제, 스키마 변경 대응
- **확장 관점**: 관계 설계를 통한 문서-청크, 계층, Collection 간 연계 처리

즉, Schema 설계는 데이터 분석 결과를 실제 시스템 구조로 옮기는 다리 역할을 하며, 이후 검색·응답 품질평가와 성능/정합성 개선의 기반이 된다.
